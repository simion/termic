# Data model

## Directories

Three directories, different owners:
- `~/Library/Application Support/termic/` — app-owned: `projects.json`, `tasks/`, `scratch/`, `settings.json`. With PROFILES (GH #280) those four are the ROOT profile's; every other profile keeps its own copy under `profiles/<slug>/`, and `profiles.json` (the registry) sits alongside them and is ABSENT until the first profile is created. `lib.rs#global_dir()` is the machine-wide root (tokens, docker, `servers/`, `backups/`, and the sandbox deny rule, which must cover every profile); `lib.rs#profile_dir(id)` is one profile's. See [profiles.md](profiles.md). Docker mode adds three more here: `docker/` (the editable Dockerfile + build metadata), `docker-agents/<agent>/` (one container config dir per agent, so a login survives `--rm`) and `docker-forge/config/{gh,glab-cli}` + `docker-forge/azure/` (the gh / glab / az logins — the host layout mirrors each container path minus the leading dot, SHARED by every agent and task, see [sandbox.md](sandbox.md)). Path via `dirs::data_local_dir().join("termic")` in `lib.rs#global_dir()` (renamed from `data_dir()` when profiles landed, so a caller that wants machine-wide state has to say so).
- `<global_dir>/sync/` + `<global_dir>/sync-state.json`: config sync (`config_sync.rs`, the idea doc is [ideas/config-sync.md](ideas/config-sync.md)). `sync/` is ONE git clone per machine of the user's private sync repo, holding `README.md`, a machine-wide `prefs.json` (the unscoped "sync" keys of `src/lib/prefsRegistry.ts`), `themes/`, and `profiles/<sync-id>/` per bound profile (`profile.json` with its name, `projects/<id>.json`, `agents/<id>.json`, `settings.json`, the profile-scoped `prefs.json`, and `removed.json` tombstones). Every file is sorted-key, pretty-printed JSON with a trailing newline. `sync-state.json` is never committed: last sync time and error, the files a rebase stopped on and the choice made for each, and the notices a pull applied until dismissed (safety-default changes, and custom agents deleted on another machine, which are applied rather than asked because they delete no files). Both live inside the data dir on purpose: the Seatbelt deny covers them and Docker mounts only named subfolders, so a caged agent can neither read the setup nor push to the repo (see [sandbox.md](sandbox.md)).
- `$TMPDIR/termic-attachments/` — files handed to an agent as FILES rather than as text: `<task_id>/` for a staged drop, `clipboard/` for an image pasted into a terminal (`clipboard_image_save`, pruned after 7 days). Deliberately NOT under the app data dir, which the Seatbelt profile ends by denying outright (CLI token); `$TMPDIR` is on `builtin_runtime_paths` and is mounted read-only into every Docker container at the same absolute path. `lib.rs#attachments_dir()`.
- `~/Library/Application Support/com.simion.termic/` — tauri-plugin-window-state owned (window position/size). Path from `tauri.conf.json#identifier`.
- `~/.config/termic/themes/` — user-owned, hand-authored custom theme files ([docs/themes.md](themes.md)). `$XDG_CONFIG_HOME` respected; shared by release + dev builds (no `termic_dev` split). Path via `lib.rs#themes_dir_path()`. Also holds `ghostty-*.json` / `warp-*.json`, saved copies of picked Ghostty / Warp themes, whose own dirs termic only reads (`theme_import.rs`).

Prefs and UI state live in the webview's `localStorage`, separate for dev and
release builds because they are different webview origins.
`src/lib/prefsRegistry.ts` lists every key: whether it is profile-scoped, and
whether it is a portable preference or tied to this machine.

## Entities

- **Project** (`projects.json`, single JSON array) — git repo path (which need NOT be the repository ROOT: pointing termic at `packages/app` of a monorepo makes that directory the project, and git then phrases its own paths differently from termic's — see [gotchas.md](gotchas.md) "git speaks repo-root paths") + scripts + `preview_url` template + `preview_browser` (GH #245, an `Option<String>` **on purpose**: absent = follow the global `Settings.preview_browser`, `Some("")` = force the OS default for this project even when the global names a browser, `Some(cmd)` = override. A plain `String` cannot express that middle state, since empty is already spoken for by "inherit" — which is why `tasks_path`, the other project override, gets away with being one. Personal, never `.termic.yaml`: a launch command is machine-specific, so a committed `open -a "Google Chrome"` would be a silently dead link for a teammate on Linux, whereas a `preview_url` is portable) + `files_to_copy` globs (personal list wins when non-empty, else the repo's committed `.termic.yaml` one — `effective_files_to_copy`) + `default_cli` + `default_yolo` (an `Option<bool>` on purpose, like `preview_browser`: absent = follow the app-wide `defaultYolo` pref (Settings → Sandbox, a machine-level localStorage key), `Some(false)` = keep asking in this project even when the app says YOLO. Resolved by `projectYoloDefault` in the FRONTEND only, which then sends `yolo` on the create; Rust never falls back to it, so a create that omits `yolo` (the CLI, MCP) gets it off. Personal, never `.termic.yaml`: a committed file must not be able to switch approvals off for whoever clones the repo) + `extra_named_ports` (personal env-var-name list for GH #196, unioned with the repo's committed `.termic.yaml` `extra_named_ports`; yaml order first, deduped, invalid/reserved names dropped — see `effective_extra_named_ports`) + optional `group` label (UI-only collapsible folder in the sidebar; no filesystem effect; a group exists iff ≥1 project carries the label. All group reads go through `groupOf()` in `src/lib/projectGroups.ts`, THE normalization point: trim + ALL-CAPS, so mixed-case labels on disk converge to one group. Collapse state + folder color live in `localStorage` keyed by normalized name, pruned when a group disappears).
- **ProjectMember** (inline in `projects.json`, multi-repo projects only) — one repo mountable inside a task under a multi-repo project (the New Task dialog can mount a subset; members it lists are the pool a task draws from). Self-contained (`root_path` + `name` + `base_branch`), never a reference to a registered Project. Carries its own `setup_script` / `run_script` / `archive_script` and its own `files_to_copy` globs, all with the same resolution rule: the value here wins when non-empty, otherwise **that member repo's OWN committed `.termic.yaml`** (`member_effective_script`, `member_effective_files_to_copy`). Which gitignored files a repo needs is a property of that repo, which is why the list sits here and not on the host — the host project's own `files_to_copy` covers the task ROOT (the host worktree) and nothing else. Frozen onto each task's `composition` at create (`TaskMember`), so editing a member's *spec* only affects future tasks — but the composition itself CAN change on a live task: `task_update_members` adds members not yet in it (materialized exactly like create — worktree or link, files copied, a port claimed from the task's `PORT_BLOCK_BUFFER` tail, setup script streamed) or removes existing ones (worktree members via `git worktree remove --force`, link members by unlinking only Termic's symlink; branches are never deleted). Removals run before additions so a same-call add can reuse a freed `dir_name` and port slot. The copy runs for worktree members only: a repo-root member IS the live checkout and already holds its files. GH #264.

`files_to_copy` patterns resolve against their source repo root and keep the
same relative path in the worktree. `.env*` matches at the root;
`**/.env*` matches at the root and in nested directories. Exact paths and
directory names also work, copying a named directory's contents recursively.
Wildcard scans skip `.git` and do not descend through directory symlinks.

- **Profile** (`profiles.json`, GH #280) — `slug` (frozen at creation; keys the data dir, the worktrees base AND the window label, so a rename never touches it), `name`, `accent` (a palette KEY from `src/lib/accents.ts`, not a hex), `order`, `last_focused_at` (Chrome's tie-break for a project living in several profiles), `open_at_quit` (launch restore). `Registry.root_slug` names which profile owns the app data dir itself, and may be `None` once that profile is deleted: nothing is promoted and nothing moves. **Task and Project each carry an in-memory `profile` tag** (`#[serde(skip)]`, so nothing reaches disk and there is no schema bump) derived from the directory the record was read from — that tag is the whole mechanism, see [profiles.md](profiles.md).
- **Task** (`tasks/<uuid>.json`) — git worktree branched from project's `base_branch`. Worktrees live at `~/termic/tasks/<project>/<name>/` by default (configurable per project and globally; a non-root profile is seeded with `~/termic/profiles/<slug>/tasks`). `is_main_checkout=true` tasks point at the project's live checkout (no worktree, archive skips `rm -rf`). `checkout_existing=true` tasks checked out an EXISTING branch instead of cutting one (New Task's "Existing branch" mode, `termic new --checkout`), so their `base_branch` is only the diff baseline, and a restore brings a branch deleted at archive back from the remote instead of cutting it from the base (`ensure_restore_branch`); older records deserialize false. `agent_args` is the ordered per-task argv created by `termic new --arg/--model`; it is appended after the selected agent's Settings args on every default-tab spawn and resume, but never reaches secondary or different-agent tabs. `yolo` is set by the create itself (`CreateTaskArgs.yolo`, `CreateMultiArgs.yolo`, `task_open_repo`'s and `task_import_worktree`'s `yolo`, all unset = off) so the FIRST spawn already carries `yolo_args`, and afterwards by `task_set_yolo`; a caged task stores `false` because spawn turns YOLO on for it anyway (`isTaskCaged`). Optional `order` holds the sidebar position within the project, written by drag-to-reorder (`task_reorder`). Projects get their order from the `projects.json` array; tasks are a file each, so they need the explicit key. `load_tasks` sorts on `(order, created)` with a missing `order` LAST, which is why a project nobody has dragged still reads oldest-first and a new task appends at the bottom of a reordered one. Optional `group` (`{ id, name?, color? }`) is the sidebar task group: `id` is the LEAD's task id (the orchestrator whose agent ran `termic new`), every member carries an identical copy (no registry file, so a group needs nothing but its members and rides their profile), `name` absent means "follow the lead's current name", `color` is an accent key. Like a project folder, a group exists while any live task carries it, a group of one included; leaving never touches the other members, and Ungroup (`task_group_dissolve`) clears them all. Naming the group of an UNGROUPED task over the CLI or MCP (`set_task_group`) joins the project's live group that already shows that name (`groupMemberByName`, trimmed and case-insensitive) rather than founding a second one, because a caller outside any task has only the name to say which tasks belong together; a task already in a group is renamed, never moved. A group made by hand (`task_group_new`) takes the task's own id, or a fresh uuid plus the task's name when that task already leads another group whose members still carry its id. Archived members keep their tag so a restore finds its group again. A group never spans projects (`apply_group_join` refuses). Optional `spawned_by` is the id of the task whose agent created this one through the CLI or MCP, or the schedule parent a scheduled run belongs to, written by `task_link_spawn` whether or not the two share a group: it is the only link for a child in another project. Cosmetic only: the id that founds a group is caller-asserted (`$TERMIC_TASK_ID`), so nothing may key a permission off it. Each task also owns a consecutive **port block** (GH #196), allocated at create by `allocate_task_ports`: `port` ($TERMIC_PORT) + one port per composition member (base+1+i) + `extra_named_ports` (frozen name→port pairs from the project's effective list, injected wherever TERMIC_PORT is set and expanded in the preview URL) + a 5-port buffer. The block length is stored on the task (`port_block_len`) at allocation; blocks first-fit over non-archived tasks from the bottom of the configured port range (`task_port_min`/`task_port_max`, default 18100-65535, GH #271; archived blocks are reused; restoring re-homes a block another task claimed meanwhile). Occupancy means "another task owns it", never "the OS says it is free": termic does not probe, so picking a range nothing else on the machine uses is the user's call, and a server started on a port something else already holds fails to bind in its own run tab. A range with no room left fails the allocation loudly at task create; `top_up_extra_ports` instead logs and keeps the pairs it has, because failing a spawn over one missing named port would be worse. Note `PORT_ALLOC_MIN` (1024) is the "this record predates port blocks" sentinel and is deliberately NOT the configurable floor: sharing them meant raising the floor above an existing task made that task's block invisible to every occupancy scan. Every load-occupancy→allocate→persist sequence holds `PORT_ALLOC_LOCK`, so concurrent creates / restores / top-ups can't scan the same snapshot and claim the same ports. This replaced the old `18100 + task count` formula, which could collide with multi-repo member ports. Names added to the config LATER reach existing tasks lazily: every tab spawn / run-script launch calls `top_up_extra_ports`, which freezes missing names into the task's buffer slots, overflowing to the next free single port anywhere once the buffer is full (`task_port_intervals` counts those strays as occupied for all later allocations; a restore re-home re-compacts them into a fresh contiguous block). Frozen pairs never move; names removed from the config keep injecting. Pre-existing tasks deserialize with an empty pair list and pick names up the same way.
- **Agent accounts** (on the agent entry in `settings.json`, GH #278) — `accounts` (names, in the order added), `default_account` (what new tasks use), `adopted_account` (the one that IS the agent's pre-existing login and therefore relocates NOTHING). Profile-scoped for free, since `settings.agents` is. `Task.accounts` (agent id -> account name) is the per-task override a switch writes; absent means "follow the agent's default". The login STORES are global and keyed by NAME (`logins/<agent>/<name>/`, `docker-agents/<agent>/<name>/`), so two profiles using the same name share one login. See [agent-accounts.md](agent-accounts.md).
- **Settings** (`settings.json`) — `preview_browser` (GH #245: app-wide command template that opens preview URLs and terminal links; empty = OS default), `repos_dir`, `welcomed`, `agents[]` (claude/gemini/codex defaults + customs; each has `command`/`args`/`yolo_args`/`runtime_yolo_command`). Defaults seeded if `agents` is empty. `schema_version` gates one-time on-disk migrations. `task_port_min` / `task_port_max` (GH #271) are the window port blocks are allocated from; 0 on either means the default 18100-65535, so read the pair through `PortRange::from_settings` (Rust) or `resolvePortRange` (`src/lib/portRange.ts`), never raw.
- **Sync state** (`Settings.sync`, `config_sync::SyncLocal`, per profile, absent until the profile first connects so an install that never syncs keeps byte-identical settings): `sync_id` (binds the profile to `profiles/<sync_id>/` in the sync repo, picked at first connect), `skipped` (project ids this machine will not register: skipped from the waiting list, or removed here), `removed` and `kept` (outboxes: removals made here and Keep answers, cleared once a push carries them), `aliases` (sync id -> local id, for a repo that was already a project here when the same project arrived from another machine; the local id never changes, tasks reference it). Only the `sync_*` commands write it: `settings_save` carries the disk copy across like the account fields. Which fields of Project, ProjectMember, Settings and Agent sync is the `*_SYNC` / `*_LOCAL` lists in `config_sync.rs`, pinned by a test that fails on a field in neither; `Agent.env` and `docker_env` never sync. `opted_out` is set by Disconnect while other profiles still sync, so the profile is not uploaded again by itself; machine-wide `sync-state.json` carries `ignored_folders`, the repo folders whose profile was deleted here.
- **Scratchpad** (`scratch/<task_id>/index.json` + `scratch/<task_id>/<pad_id>.txt`, GH #244) — an untitled buffer that survives a relaunch, scoped to ONE task. Stored here rather than in the worktree so it never appears in `git status`, in the agent's review diff, or in a commit. The index record (`id`, `title`, `syntax`, `order`, `created_at`, `updated_at`) exists because a pad has no filename to re-derive a title or syntax from, and one index read beats stat-ing N files on launch. Pads are NOT part of `persisted_tabs`, which is agent-tabs-only by construction; they restore from this index when their task is first entered.
- **Shared scratchpads** (GH #385) — three more scopes beside the task's, each a plain DIRECTORY TREE of files the user names (no index, no untitled buffers): **project** at `<profile_dir>/scratch/projects/<project_id>/`, **profile** at `<profile_dir>/scratch/profile/`, and **global** at `<root_profile_dir>/scratch/global/`, the one copy every profile sees. `scratch_dir` in `lib.rs` routes all four from one target id (`<task_id>`, `project_<id>`, `profile_<slug>`, `global`). They outlive the task that wrote them, which is the point: a finding one agent leaves in the project pad is there for the next task. Every path a command takes is checked against the scope's root (`reject_escaping_segments`: no `..`, no rooted or drive-relative segment, on every platform), and a symlink is not listed in the tree, nor followed by the sync export. Config sync mirrors the three shared scopes (never the task pads): global under `scratch/` at the repo root, profile under `profiles/<sync_id>/scratch/`, project under `profiles/<sync_id>/scratch/projects/<project_sync_id>/`.
- **Tab properties** (`PersistedTab.props` on a task's `persisted_tabs`, `TerminalTab.props` live, GH #358): `{ key, value, since }`, in the order they were set; `since` (epoch ms) is when the key was FIRST set on the tab, so an update keeps the key where it is. Set by agents through `termic prop` / MCP `task_prop` on their own tab (`$TERMIC_TAB_ID`, injected into every agent PTY on the host and, through the env overlay, in Docker). The webview store is the ONLY writer (`setTabProp`, reached by the `tab_props` RPC): the list rides every `task_set_tabs`, so a Rust-side write would be overwritten by the next sync. The task row shows the collected view (`lib/tabProps.ts collectTaskProps`): one entry per key, keys by earliest first-set, each key's distinct values joined with ", " in tab order. Closing a tab drops its properties; shell tabs are not durable, so theirs do not survive a relaunch. Limits live in `termic-proto` (`prop_key_problem`, `prop_value_problem`, 8 keys per tab). Empty is not serialized.
- **Tab subgroups** (`PersistedTab.subgroup` on a task's `persisted_tabs`, `TerminalTab.subgroup` live): `{ id, name, color? }` (`color` an accent key), the subgroup a main-pane tab sits in inside its task's sidebar tree (docs/ui.md "Tab subgroups"). Every member carries an identical copy, like `Task.group`; there is no subgroup list anywhere, and a subgroup exists while one tab carries it. Absent is the only "ungrouped" state: the store writes no key and Rust skips `None`, so a task file from before the field reads and writes back unchanged. Main pane only, and that is the store's guard: `durablePersistedTabs` sends it only for main-pane tabs, while Rust keeps whatever `task_set_tabs` is sent (`merge_persisted_tabs` drops it only without `keep_pane`, the right panel's tabs). Never on a pinned tab. Written by `task_set_tabs` with the rest of the record; its no-op check (`same_persisted_tabs`) compares it, or a subgroup-only change would never reach disk. Shells are not durable, so a shell-only subgroup is gone after a relaunch. Fold state is UI-only: `collapsedTabSubgroups` in scoped localStorage. Downgrading to a build without subgroups loses them: an older build ignores the unknown key on read and drops it on its next write of that task file (any `save_task`, not only a tab change), so the tabs come back loose when upgrading again.
- **Scheduled queue messages** (`PersistedTab.scheduled` on a task's `persisted_tabs`, GH #300) — `{ id, text, not_before, created }` (epoch ms). A queue message with a "send after" date, one-shot. It lives on the TAB record because it belongs to that chat's session: an archived task never mounts, so it never sends; a restore brings it back; closing a secondary tab (which drops the record) deletes it, and the close asks first. Only scheduled items persist; ordinary queue items stay runtime-only. Written solely by `task_set_tab_scheduled`; `task_set_tabs` carries it forward by tab id like `session_id` (`merge_persisted_tabs`), so a rename racing a schedule write cannot drop it. Empty is not serialized, so older task files are unchanged. On restore `ensureDefaultTab` hydrates it into `tab.queue` as items with `notBefore`.

  **Archiving a task leaves its pads alone.** Archiving is recoverable (the task stays in History, the branch stays in git) and notes about the work are exactly what someone wants back when they restore it. The only thing that deletes pads is `delete_task_file`, the hard delete behind History's "Empty archive" and project removal — pinned by `only_the_hard_delete_purges_scratchpads` in `lib.rs`.
- **Recurring schedules** (`Task.schedule`, GH #300, `src-tauri/src/schedules.rs`): set only on a schedule's PARENT task, absent everywhere else (older files unchanged): `enabled`, `name`, `slug` (the report folder's name, fixed at creation; `task_set_schedule` refuses a change, and refuses a slug another schedule in the project owns, archived parents included), `prompt` and/or `prompt_id` (a prompt-library entry, resolved at fire time; with both, the body comes first, the CLI's `-P` + `-p` composition), `cadence` (`{ kind: "daily" | "weekdays" | "weekly", time: "HH:MM", weekday? }`, local wall clock, `weekday` 0 = Sunday), `catch_up`, `keep_runs` (1-20), `report_days` (7/30/90 or `null` for forever; written as 30 at creation, so `null` only ever means the user chose forever), `last_slot` (epoch ms, only moves forward) and `history` (newest last, about 30 entries: `{ slot, outcome: running | fired | no_report | needs_input | missed | skipped | failed, run_task_id?, report?, title?, count?, error?, manual?, report_gone? }`). Written solely by `task_set_schedule`, always the whole record; every other writer is a load-modify-save of the whole task and carries it forward (pinned in `lib.rs`'s `schedule_record_tests`). A schedule cannot be CREATED on a Docker task. **Runs** are ordinary main-checkout tasks in the parent's group with `spawned_by` = the parent; they need no field of their own, and only ids in `history` are ever archived by the scheduler, never "any task the parent spawned" (the parent's own agent can spawn tasks through the CLI). **A run inherits its parent's agent, `agent_args`, YOLO, sandbox and account override**, passed explicitly at create; that rule lives in ONE place, `runSpecFromParent` (`src/lib/schedules/runSpec.ts`), and nowhere else: no create path inherits YOLO or the sandbox by itself, and a task created through the CLI or MCP still does not. The maintainer reserved a say on YOLO and the sandbox; the alternative ("YOLO off and the project's sandbox unless the schedule opts in") is a change to that function plus one schedule field. **Reports** are `<project>/.termic/schedules/<slug>/<YYYY-MM-DD_HHMM>.md` (or `.html`), written by the run's agent into the live checkout, which is the one place a caged agent can write (Seatbelt allows the task dir). Creating a schedule makes the folder and appends `/<project path below the repo root>/.termic/schedules/` to the repo's common-dir `info/exclude` (never `.gitignore`), so reports never show in `git status`. `.termic/` is shared with the optional `.termic/tasks` worktrees root and is not the scheduler's to clean. Retention deletes only report-named regular files directly in the schedule's own folder, dated by the NAME (never the mtime), never through a symlink, after each run and once at launch; deleting a schedule keeps its reports unless asked.
- **Tab** (per task, in `useApp`) — `terminal` (PTY running a CLI), `edit` (CodeMirror), `diff` (vs HEAD), `dir` (folder listing), `scratch` (an untitled buffer, GH #244 — a distinct type rather than an `EditTab` with an empty `path`, so blame / review comments / the disk-watch banner / "locate in file tree" become compiler errors to answer rather than runtime surprises). PTYs die with the app.

## Migrations

The "Task" entity was called "Workspace" before, on disk and in code. A one-time
startup migration (`migrate_workspaces_to_tasks` in `lib.rs`, gated by
`settings.schema_version`) renames the metadata dir `workspaces/` → `tasks/` and
rewrites the `is_repo_root` field to `is_main_checkout` (serde `alias` still reads
the old name). It is **metadata-only**: it deliberately does NOT move worktree
directories or rewrite each task's `path`. CWD-resume agents (Claude Code's
`--continue`) resume the most recent session by working directory, so relocating a
worktree would silently orphan its history. Existing worktrees stay under
`~/termic/workspaces/…`; NEW worktrees are created under `~/termic/tasks/…`
(`default_worktrees_base()`), and the two roots coexist while the old one empties out
lazily as tasks are archived/recreated. The metadata rename is atomic (stage in
`tasks.tmp/`, then one `rename` into place), guarded by a `tasks-migration.lock`,
backs up to `backups/pre-tasks-<ts>/`, and prunes-on-corruption (an unparseable
record, or an active worktree whose dir was deleted externally, is dropped +
logged to `tasks-migration.log`, never carried forward). The JS half
(`src/lib/lsMigration.ts`) renames the persisted `localStorage` pref keys
(`workspaceExpandMode` → `taskExpandMode`, `collapsedWorkspaces` → `collapsedTasks`,
plus the two `newWorkspaceLast*` keys); everything else in `localStorage` kept its
name, and the per-task records among it are keyed by task UUID, which never
changes. Every key, the old names included (marked `legacy`), is listed in
`src/lib/prefsRegistry.ts`.


### Per-tab launch arguments

Agent tabs created through the CLI/MCP may carry `agent_args` in their
persisted tab record (`agentArgs` in the frontend). These arguments follow
registry defaults, precede managed resume/runtime arguments, and survive
close/reopen and application restart. They do not change Settings or the
task's default agent. Empty arguments remain absent from serialized tabs.

Only the durable default tab can inherit legacy task-level resume history.
A new secondary tab starts a fresh session even if it is the first tab of a
different profile. Explicit `tab --resume SESSION_ID` and restoration of a
tab's own captured session continue to resume that specific session.
